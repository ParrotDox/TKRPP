# Тестирование: сценарии, сквозной сценарий и спецификации unit-тестов

**Лабораторная работа № 5.** Репозиторий: https://github.com/ParrotDox/TKRPP.git
**Основано на:** критериях приёмки лаб. № 2 ([user-stories.md](requirements/user-stories.md)), модулях лаб. № 3 ([modules.md](architecture/modules.md)) и составе спринтов лаб. № 4 ([sprint-01.md](planning/sprint-01.md), [sprint-02.md](planning/sprint-02.md)).

## 1. Объём тестирования

Проверяем ключевую часть MVP — область спринта 1 и, частично, спринта 2:

- **Возможности (истории):** US-03-02 (загрузка файлов), US-03-01 (генерация), US-03-03 (настройки промпта, минимально). После спринта 2 добавляются US-01-01, US-01-03, US-02-03, US-03-05 (раздел «E2E и тесты после спринта 2»).
- **Модули:** «Обработка и парсинг документов», «Взаимодействие с ИИ» (обе — серверная логика C#, unit-тесты xUnit); «UI» — руками и сквозным сценарием (unit-тесты на чистый JS не планируются).
- Это не весь продукт: Should/Could-функции (поиск, экспорт, печать) в объём не входят.

## 2. Тестовые сценарии

### TS-01 (US-03-02, успешный)

- **Дано:** открыто окно генерации; файлы не выбраны; зона загрузки в состоянии «нет файлов».
- **Когда:** пользователь перетаскивает валидный PDF «лекция.pdf».
- **Тогда:** файл отображается в списке; зона переключается в состояние «файлы есть»; кнопка «Сгенерировать» активна; содержимое файла на клиенте хранится до отправки.

### TS-02 (US-03-02, отрицательный)

- **Дано:** открыто окно генерации.
- **Когда:** пользователь выбирает файл недопустимого формата (например, `.exe` или переименованный бинарник).
- **Тогда:** файл отклоняется с сообщением о недопустимом формате; в список загрузки не попадает; генерация не запускается.

### TS-03 (US-03-01, US-03-03, успешный)

- **Дано:** загружен валидный PDF с текстовым слоем; выбраны настройки «Кратко / Разговорный / Конспект»; поле пожеланий пустое.
- **Когда:** пользователь нажимает «Сгенерировать» и ждёт до 30 секунд.
- **Тогда:** отображается индикатор загрузки; по завершении на экране — предпросмотр карточки с полями **Тема, Summary, Конспект, Задания, Ключевые слова**; настройки пользователя учтены в запросе.

### TS-04 (US-03-01, граничный)

- **Дано:** загружен валидный PDF; сеть или сервис ИИ недоступны (или таймаут 30 секунд).
- **Когда:** пользователь нажимает «Сгенерировать».
- **Тогда:** индикатор завершается; отображается понятное сообщение об ошибке и кнопка «Повторить генерацию»; ранее отображённые данные не искажаются; приложение продолжает работать.

### TS-05 (US-03-02, граничный)

- **Дано:** подготовлен пустой файл (0 байт) и PDF без текстового слоя (только скан).
- **Когда:** пользователь загружает такой файл и нажимает «Сгенерировать».
- **Тогда:** парсинг возвращает «текст не извлечён»; запрос к ИИ не отправляется; пользователь видит сообщение «Не удалось извлечь текст из файла» без падения приложения.

## 3. Сквозной (end-to-end) сценарий

### E2E-01. Главный путь спринта 1 (US-03-02 → US-03-03 → US-03-01)

1. Исходно: приложение открыто, окно генерации пустое.
2. Пользователь перетаскивает «лекция.pdf» в зону загрузки. *(UI → Обработка документов)*
3. Пользователь видит на экране извлечённый текст. *(Обработка документов ← UI)*
4. Выбирает параметры: «Кратко», «Разговорный», «Конспект», добавляет пожелание «с примерами». *(UI — сборка запроса)*
5. Нажимает «Сгенерировать», видит индикатор загрузки. *(UI → ИИ-модуль → LLM API)*
6. **Итог:** на экране отображается карточка: тема, summary, конспект с примерами, задания, ключевые слова; повторное нажатие «Сгенерировать» работает без перезапуска приложения.

Путь подтверждает, что пользователь получает законченную пользу (конспект без ручной работы), а не наличие отдельных модулей.

### E2E-02. Сценарий демонстрации MVP (после спринта 2)

Проходится по 7 шагам из [mvp.md](requirements/mvp.md): просмотр экрана → создание колоды → загрузка PDF → сохранение сгенерированной карточки в колоду → открытие колоды и проверка карточки → проверка общего хранилища → удаление карточки/колоды. Затронуты все пять модулей: UI → Обработка документов → ИИ → Управление данными → Локальное хранение.

| № | Модуль / функция | Вход (данные и исходное состояние) | Ожидаемый выход | Класс случая |
|---|---|---|---|---|
| UT-01 | Парсинг / `ParsePdf` | Валидный PDF с текстовым слоем (2 стр., известные слова) | 200: непустая строка, содержит выборочные слова документа (не весь мусор, порядок сохранён) | успешный |
| UT-02 | Парсинг / `ParseTxt` | Валидный `.txt`, кодировка UTF-8 | Возвращённая строка == содержимому файла (возможна нормализация переводов строк — только `\n`) | успешный |
| UT-03 | Парсинг / `ParsePdf` | Бинарные байты с расширением `.pdf` | Ошибка/400, код `ERR_BAD_FILE`; текст не возвращается | отрицательный |

## 7. Ответы на контрольные вопросы (лаб. № 5)

1. **Тестирование не доказывает отсутствие ошибок** — оно демонстрирует наличие дефектов в обнаруженных сценариях и даёт команде два эффекта: уверенность в конкретно проверенном поведении и защиту от регрессий при изменениях кода.
2. **Критерии приёмки → сценарии:** формат почти дословный — «Дано» берётся из исходной ситуации критерия, «Когда» — из его действия, «Тогда» — из наблюдаемого результата; сценарий — это критерий приёмки, переписанный в форме проверки (см. TS-01 из US-03-02).
3. **Классы эквивалентности** делят входы на группы с одинаковым поведением (валидный PDF; недопустимый формат; пустой файл), тест берёт по представителю из каждого класса. **Граничные значения** — края диапазонов и точки рядом с ними (0 байт; PDF без текстового слоя; 30-секундный таймаут), где ошибки возникают чаще всего.
4. **Unit vs e2e:** unit-тест проверяет одну операцию модуля в изоляции — быстрые, их много, точно локализуют дефект; e2e-сценарий проверяет весь пользовательский путь через все модули — медленный, один-два на MVP, он подтверждает, что продукт даёт пользу целиком (E2E-01), а не что модули существуют по отдельности.
5. **Спецификация unit-теста** содержит: что проверяем (функция модуля), вход и исходное состояние, ожидаемый выход, класс случая. Ожидаемый выход должен быть проверяемым, чтобы любой участник мог однозначно сказать «прошло/не прошло»: «возвращает код ERR_EMPTY_FILE и не инициирует запрос к ИИ», а не «обрабатывает корректно».
