## 1. Объём тестирования

- **Спринт 1** — загрузка и извлечение текста: US-03-02 (полностью), каркас US-0N (навигация и состояния на моках, проверяется руками). Модули: «Обработка и парсинг документов», API-слой.
- Unit-тесты — на серверную логику парсинга (C#, xUnit).

## 2. Тестовые сценарии

### TS-01 (US-03-02, успешный) — спринт 1

- **Дано:** открыто окно генерации в браузере; файлы не выбраны; зона загрузки в состоянии «нет файлов».
- **Когда:** пользователь перетаскивает валидный PDF «лекция.pdf».
- **Тогда:** файл отображается в списке; зона переключается в состояние «файлы есть»; кнопка «Извлечь текст» становится активной.

### TS-02 (US-03-02, отрицательный) — спринт 1

- **Дано:** открыто окно генерации.
- **Когда:** пользователь выбирает файл недопустимого формата (например, `.exe` или переименованный бинарник).
- **Тогда:** файл отклоняется с сообщением о недопустимом формате; в список загрузки не попадает; запрос на `/api/parse` не отправляется.

### TS-03 (US-03-02, граничный) — спринт 1

- **Дано:** открыто окно генерации; подготовлен пустой файл `.txt` (0 байт).
- **Когда:** пользователь загружает пустой файл и нажимает «Извлечь текст».
- **Тогда:** `/api/parse` возвращает ошибку с кодом `ERR_EMPTY_FILE`; пользователь видит сообщение «Файл пуст»; остальные элементы экрана не ломаются.

### TS-04 (US-03-02, граничный) — спринт 1

- **Дано:** открыто окно генерации; подготовлен PDF только со сканом (без текстового слоя).
- **Когда:** пользователь загружает такой файл и нажимает «Извлечь текст».
- **Тогда:** `/api/parse` возвращает ошибку с кодом `ERR_NO_TEXT`; пользователь видит сообщение «Не удалось извлечь текст из файла»; приложение продолжает работать, состояния остальных элементов не ломаются.

## 3. Сквозные (end-to-end) сценарии

### E2E-01. Главный путь спринта 1 (US-03-02)

1. Исходно: приложение открыто в браузере, окно генерации пустое.
2. Пользователь перетаскивает «лекция.pdf» в зону загрузки. *(UI → Обработка документов)*
3. Пользователь нажимает «Извлечь текст». *(UI → Обработка документов → API)*
4. **Итог:** на экране отображается извлечённый текст документа; при битом файле — понятная ошибка, а не падение приложения.

Путь подтверждает, что связка «браузер → API → парсер → браузер» работает как целое.

## 4. Спецификации unit-тестов («вход → ожидаемый выход»)

### Обработка документов

| № | Модуль / функция | Вход (данные и исходное состояние) | Ожидаемый выход | Класс случая |
|---|---|---|---|---|
| UT-01 | Парсинг / `ParsePdf` | Валидный PDF с текстовым слоем (2 стр., известные слова) | Возвращена непустая строка, содержит выборочные слова документа, порядок текста сохранён | успешный |
| UT-02 | Парсинг / `ParseTxt` | Валидный `.txt`, кодировка UTF-8 | Возвращённая строка == содержимому файла (нормализуются только переводы строк к `\n`) | успешный |
| UT-03 | Парсинг / `ParsePdf` | Бинарные байты с расширением `.pdf` | Возвращается ошибка `ERR_BAD_FILE`; текст не возвращается | отрицательный |
| UT-04 | Парсинг / `ParseTxt` | Файл 0 байт | Возвращается ошибка `ERR_EMPTY_FILE`; дальше по конвейеру текст не передаётся | граничный |
| UT-05 | Парсинг / `ParsePdf` | PDF только со сканом (без текстового слоя) | Извлечён пустой текст → ошибка `ERR_NO_TEXT`; текст не возвращается | граничный |

## 6. Автоматизация и Definition of Done

- **В первую очередь автоматизируем** UT-01…UT-05: это быстрые тесты парсера без UI.
- **E2E-01** в спринте 1 проходится вручную; автотесты (Playwright) — после стабилизации UI.
- **DoD:** задача считается выполненной, если для новой операции есть успешный и отрицательный/граничный unit-тест, а таблица прослеживаемости обновлена.
