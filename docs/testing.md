# Тестирование: сценарии, сквозной сценарий и спецификации unit-тестов

**Лабораторная работа № 5.** Репозиторий: https://github.com/ParrotDox/TKRPP.git
**Основано на:** критериях приёмки лаб. № 2 ([user-stories.md](requirements/user-stories.md)), модулях лаб. № 3 ([modules.md](architecture/modules.md)) и составе спринтов лаб. № 4 ([sprint-01.md](planning/sprint-01.md), [sprint-02.md](planning/sprint-02.md)).

## 1. Объём тестирования

- **Спринт 1** — загрузка и извлечение текста: US-03-02 (полностью), каркас US-0N (навигация и состояния на моках, проверяется руками). Модули: «Обработка и парсинг документов», API-слой. Автотесты для этого модуля появятся в спринте 2 (T-16).
- **Спринт 2** — генерация, хранение и колоды: US-03-01, US-03-03, US-03-05, US-01-01, US-01-03, US-02-03. Модули: «Взаимодействие с ИИ», «Управление данными и колодами», «Локальное хранение»; UI — руками и сквозным сценарием.
- Unit-тесты — на серверную логику (C#, xUnit). Это не весь продукт: Should/Could-функции (поиск, экспорт, печать) в объём не входят.

## 2. Тестовые сценарии

### TS-01 (US-03-02, успешный) — спринт 1

- **Дано:** открыто окно генерации в браузере; файлы не выбраны; зона загрузки в состоянии «нет файлов».
- **Когда:** пользователь перетаскивает валидный PDF «лекция.pdf».
- **Тогда:** файл отображается в списке; зона переключается в состояние «файлы есть»; кнопка «Сгенерировать» активна.

### TS-02 (US-03-02, отрицательный) — спринт 1

- **Дано:** открыто окно генерации.
- **Когда:** пользователь выбирает файл недопустимого формата (например, `.exe` или переименованный бинарник).
- **Тогда:** файл отклоняется с сообщением о недопустимом формате; в список загрузки не попадает; запрос на `/api/parse` не отправляется.

### TS-03 (US-03-02, граничный) — спринт 1

- **Дано:** подготовлены пустой файл (0 байт) и PDF без текстового слоя (только скан).
- **Когда:** пользователь загружает такой файл.
- **Тогда:** `/api/parse` возвращает ошибку («текст не извлечён»); пользователь видит сообщение «Не удалось извлечь текст из файла»; приложение продолжает работать, состояния остальных элементов не ломаются.

### TS-04 (US-03-01 + US-03-03, успешный) — спринт 2

- **Дано:** загружен валидный PDF с текстовым слоем; извлечённый текст отображается; выбраны настройки «Кратко / Разговорный / Конспект»; поле пожеланий пустое.
- **Когда:** пользователь нажимает «Сгенерировать» и ждёт до 30 секунд.
- **Тогда:** отображается индикатор загрузки; по завершении — предпросмотр карточки с полями **Тема, Summary, Конспект, Задания, Ключевые слова**; настройки учтены в запросе.

### TS-05 (US-03-01, граничный) — спринт 2

- **Дано:** загружен валидный PDF; сеть или сервис ИИ недоступны (или таймаут 30 секунд).
- **Когда:** пользователь нажимает «Сгенерировать».
- **Тогда:** индикатор завершается; отображается сообщение об ошибке и кнопка «Повторить генерацию»; ранее отображённые данные не искажаются; приложение продолжает работать.

## 3. Сквозные (end-to-end) сценарии

### E2E-01. Главный путь спринта 1 (US-03-02)

1. Исходно: приложение открыто в браузере, окно генерации пустое.
2. Пользователь перетаскивает «лекция.pdf» в зону загрузки. *(UI → Обработка документов)*
3. Пользователь нажимает «Извлечь текст» / загрузка отправляется автоматически. *(UI → Обработка документов → API)*
4. **Итог:** на экране отображается извлечённый текст документа; при битом файле — понятная ошибка, а не падение приложения.

Путь подтверждает, что связка «браузер → API → парсер → браузер» работает как целое.

### E2E-02. Сценарий демонстрации MVP (после спринта 2)

Проходится по 7 шагам из [mvp.md](requirements/mvp.md): открыть экран → создать колоду → загрузить PDF → сгенерировать и сохранить карточку в колоду → открыть колоду и проверить карточку → проверить общее хранилище → удалить карточку/колоду. Затронуты все пять модулей: UI → Обработка документов → ИИ → Управление данными → Локальное хранение.

## 4. Спецификации unit-тестов («вход → ожидаемый выход»)

### Спринт 1 — парсинг документов

| № | Модуль / функция | Вход (данные и исходное состояние) | Ожидаемый выход | Класс случая |
|---|---|---|---|---|
| UT-01 | Парсинг / `ParsePdf` | Валидный PDF с текстовым слоем (2 стр., известные слова) | 200: непустая строка, содержит выборочные слова документа, порядок текста сохранён | успешный |

## 5. Автоматизация и Definition of Done

- **Спринт 1:** автотесты в объём спринта не входят — проверки TS-01…TS-03 и E2E-01 выполняются **вручную** перед демонстрацией.
- **Спринт 2:** все автотесты UT-01…UT-18 (xUnit, запуск локально и по PR) реализуются в задаче **T-16**; E2E-02 — ритуал перед сдачей.
- Спецификации UT-01…UT-06 относятся к модулю парсинга, разработанному в спринте 1, но автоматизируются в спринте 2 — чтобы все проверки шли одним пакетом.

## 7. Ответы на контрольные вопросы (лаб. № 5)

1. **Тестирование не доказывает отсутствие ошибок** — оно демонстрирует наличие дефектов в обнаруженных сценариях и даёт команде два эффекта: уверенность в конкретно проверенном поведении и защиту от регрессий при изменениях кода.
2. **Критерии приёмки → сценарии:** формат почти дословный — «Дано» берётся из исходной ситуации критерия, «Когда» — из его действия, «Тогда» — из наблюдаемого результата; сценарий — это критерий приёмки, переписанный в форме проверки (см. TS-01 из US-03-02).
3. **Классы эквивалентности** делят входы на группы с одинаковым поведением (валидный PDF; недопустимый формат; пустой файл), тест берёт по представителю из каждого класса. **Граничные значения** — края диапазонов и точки рядом с ними (0 байт; PDF без текстового слоя; 30-секундный таймаут), где ошибки возникают чаще всего.
4. **Unit vs e2e:** unit-тест проверяет одну операцию модуля в изоляции — быстрые, их много, точно локализуют дефект; e2e-сценарий проверяет весь пользовательский путь через все модули — медленный, один-два на MVP, он подтверждает, что продукт даёт пользу целиком, а не что модули существуют по отдельности.
5. **Спецификация unit-теста** содержит: что проверяем (функция модуля), вход и исходное состояние, ожидаемый выход, класс случая. Ожидаемый выход должен быть проверяемым, чтобы любой участник мог однозначно сказать «прошло/не прошло»: «возвращает код ERR_EMPTY_FILE и не инициирует запрос к ИИ», а не «обрабатывает корректно».
