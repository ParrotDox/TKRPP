# План первого спринта

**Лабораторная команда по ТКРПП, проект https://github.com/ParrotDox/TKRPP.git**
**Даты:** 03.11.2026 – 17.11.2026 (две недели; при сдвиге — поправить даты в этом файле и доске).
**Состав:** 4 участника — Максим, Данил, Саня (Александр), Егор. *Отклонение от формата лабораторной («5 участников») зафиксировано и обсуждалось с преподавателем.*

## 1. Цель спринта

> **К концу спринта пользователь открывает окно приложения, загружает учебный файл (PDF/TXT), выбирает параметры генерации и видит на экране сгенерированный ИИ конспект.**

Цель сформулирована как пользовательский результат (демонстрируемый) и опирается на Must-have истории **US-03-02 → US-03-01** (минимально + US-03-03). К холодному ядру MVP (хранилище, колоды) спринт не прикасается — это спринт 2 ([sprint-02.md](sprint-02.md)).

> **Почему в спринте ничего нельзя «выкинуть»: если объём не вывозим — сокращаем состав задач, но не цель** (см. раздел «Риски»).

## 2. Истории в спринте

| История | Приоритет | Что берём |
|---|---|---|

| US-03-01 Генерация карточки | Must | Целиком (эндпоинт + предпросмотр + обработка ошибок). |
| US-03-03 Настройки промпта | Should | Минимально (радиокнопки + поле промпта), как часть окна генерации. |

## 3. Доска задач

- **Платформа:** GitHub Projects (репозиторий уже на GitHub, задачи связываются с кодом).
- **Колонки:** `Сделать` → `В работе` → `На проверке` → `Готово`.
- **WIP-лимит:** в «В работе» — не более 4 карточек одновременно.
- **Правило:** «нет карточки — нет задачи» — вся работа отражается на доске.
- **Ссылка на доску:** `<ВСТАВИТЬ ССЫЛКУ ПОСЛЕ СОЗДАНИЯ: github.com/ParrotDox/TKRPP/projects>` *(скриншот доски — в отчёт лаб. № 4)*.

## 5. Оценка в story points

- **Шкала:** 1, 2, 3, 5, 8, 13 (числа Фибоначчи).
- **Опорная задача (эталон): T-01 = 3 SP** — типовой экран на HTML+CSS, понятен всем; оценки остальных даны относительно него.
- **Объём спринта:** базовый **27 SP** (без T-08); с растяжимой T-08 — **30 SP**.
  - Первому спринту velocity неизвестна, объём берём умеренно. Если к середине спринта видно невывоз — **T-08 переносим в спринт 2**, базовый объём не трогаем.
- По итогам спринта фиксируем факт: сколько SP закрыто фактически → это velocity для планирования спринта 2.

## 6. Зависимости (критический путь)

`T-01` параллельно `T-02` и `T-03`; `T-05` зависит от `T-02, T-03`; `T-06` — от `T-05`; `T-04` и `T-07` — связаны фронту с бэком через контракт `T-03`. Интеграция `T-04 ↔ T-05` — самая рисковая стыковка, договориться о формате multipart-запроса в первый день.

## 7. Definition of Done (для задач спринта)

1. Код в ветке → Pull Request → ревью → merge в `main`.
2. Логика покрыта тестами (если задача в области T-08) или проверена вручную по критериям приёмки истории.
3. Карточка на доске переведена в «Готово» с комментарием об итоге.
4. Функциональность работает на `localhost` минимум у двух участников независимо.

## 11. Ответы на контрольные вопросы (лаб. № 4)

1. **Задача vs история.** История описывает ценность пользователя и по ней нельзя раздать работу — она слишком крупна и не имеет технического «how». Задача — конкретный инженерный шаг с исполнителем, условием завершения и зависимостями; истории декомпозируются на задачи по модулям/слоям (данные/логика/интерфейс), иначе нельзя поручить и проверить работу.
2. **Story point.** SP — условная единица относительного размера задачи, а не время. Оценка в часах систематически занижается и привязана к конкретному человеку; SP позволяет сравнивать задачи между собой, не зависеть от исполнителя и измерять velocity команды. Шкала Фибоначчи выбрана потому, что с ростом размера точность оценки падает и различать близкие значения бессмысленно.
3. **Доска задач.** Единый источник правды о состоянии: любой участник и преподаватель видят, что сделано/в работе/не начато. WIP-лимит («В работе» ≤ 4 карточек) заставляет доводить задачи до конца, а не накапливать начатые; доска делает видимой работу всей команды, а не только своих задач.
