## 1. Цель спринта

> **К концу спринта пользователь открывает приложение в браузере, загружает учебный файл (PDF/TXT) и видит извлечённый из него текст в минимальном интерфейсе; каркас UI готов под следующие экраны.**

Цель — пользовательский, демонстрируемый результат: загрузил файл → увидел текст. Спринт опирается на Must-have **US-03-02** и на каркас экранов **US-0N**; генерация (US-03-01) сознательно **перенесена в спринт 2** — [sprint-02.md](sprint-02.md).

| US-0N Просмотр сущностей | Must | Только каркас главного экрана на моках (без реальных данных). |

## 5. Оценка в story points

- **Шкала:** 1, 2, 3, 5, 8, 13 (числа Фибоначчи).
- **Опорная задача (эталон): T-01 = 3 SP** — типовой экран на HTML+CSS; оценки остальных даны относительно него.
- **Объём спринта: 19 SP** (T-01 3 + T-02 3 + T-03 2 + T-04 3 + T-05 5 + T-06 3). *Ранее было указано 24 SP по ошибке в сложении — исправлено.*
- Первому спринту velocity неизвестна, объём умеренный. Если к середине спринта видно невывоз — **T-06 переносим в спринт 2**, цель не меняем.
- По итогам спринта фиксируем факт: сколько SP закрыто фактически → это velocity для планирования спринта 2.

## 6. Зависимости (критический путь)

`T-01` параллельно `T-02` и `T-03`; `T-05` зависит от `T-02, T-03`; `T-04` — от `T-01, T-03, T-05`; `T-06` использует стили/каркас из `T-01`. Самая рисковая стыковка — `T-04 ↔ T-05` (формат multipart-запроса), договориться в первый день.

## 7. Definition of Done (для задач спринта)

1. Код в ветке → Pull Request → ревью → merge в `main`.
2. Функциональность проверена вручную по критериям приёмки истории (автотесты — в спринте 2, задача T-16).
3. Карточка на доске переведена в «Готово» с комментарием об итоге.
4. Функциональность работает на `localhost` минимум у двух участников независимо.

## 11. Ответы на контрольные вопросы (лаб. № 4)

1. **Задача vs история.** История описывает ценность пользователя и по ней нельзя раздать работу — она слишком крупна и не имеет технического «how». Задача — конкретный инженерный шаг с исполнителем, условием завершения и зависимостями; истории декомпозируются на задачи по модулям/слоям (данные/логика/интерфейс), иначе нельзя поручить и проверить работу.
2. **Story point.** SP — условная единица относительного размера задачи, а не время. Оценка в часах систематически занижается и привязана к конкретному человеку; SP позволяет сравнивать задачи между собой, не зависеть от исполнителя и измерять velocity команды. Шкала Фибоначчи выбрана потому, что с ростом размера точность оценки падает и различать близкие значения бессмысленно.
3. **Доска задач.** Единый источник правды о состоянии: любой участник и преподаватель видят, что сделано/в работе/не начато. WIP-лимит («В работе» ≤ 4 карточек) заставляет доводить задачи до конца, а не накапливать начатые; доска делает видимой работу всей команды, а не только своих задач.
